## 1. Purpose

Reduce **institutional repetition** without weakening boundary integrity.

Hedgr’s important protections still earn their cost. Excess load is accumulating in how those protections are repeatedly represented, rebound, and re-instantiated for small units of reversible work. Path B changes **where history is consumed**, **when RAP provenance is a separate human epoch**, and **how many authority epochs sit inside one already named outcome**. It does not change what is protected.

The three forks are independent. Accepting this design as a package does not require implementing all three on the same day. Rejecting one later does not unwind the others unless the Founder says so.

## 5. Fork 1 — Live present-state versus historical record

### Target

Make the **live authority surface** concise and limited to **present operative truth**. Keep completed decisions and chronology in **historical records**, ADRs, git, and completed numbered sections.

History continues to exist. Operators stop having to reconstruct current occupancy from a memoir that also contains superseded sentences.

### Live present-state (proposed contents)

A single operative block, owned by **§7** (with **§7a** holding the active brief for whatever §7 names), limited to:

1. Named parent tickets and, when present, named nested tickets.
2. Authority class / Yellow-Red / execution class for each named lane.
3. Parallelism pass in force (currently Controlled Parallelism v22 / §6f.22, G deferred).
4. Exact exclusions, stop conditions, and rollback pointers for the occupying brief (or a pointer to the live §7a subsection).
5. Distribution / publication / financial / Green flags currently in force.
6. Pointers to the historical record for closed tickets and completed decisions.

`AGENTS.md` live block would point operators to that present-state block rather than restating the same chronology. Dated “Current / Historical” override stacks would become historical record, not a second live canon.

RAP would continue to project recorded fields with provenance. It would not be redesigned here as a human dashboard. Nested ticket names may later be added as **non-activating pointers** only if a separate RAP-schema decision is taken; that is not required to accept Fork 1.

### Historical record (retained)

- Numbered `HEDGR_STATUS.md` completed-decision sections.
- Accepted ADRs and the Sprint 2 ADR index.
- Git history and merged PR records.
- Closed-ticket briefs retained in §7a as **completed historical** subsections, clearly labelled so they cannot be misread as occupancy.

AUTHORITY-LEGIBILITY-001 remains: authority correctness and authority legibility are separate; lag is surfaced, never silently repaired, never used to infer a second authority. Thinning the live surface is the *cure* for reconstruction cost; it is not a silent rewrite of history.

### What Fork 1 does not do

- Does not delete completed § records, ADRs, or git.
- Does not authorise a STATUS/AGENTS thinning pass in this artefact.
- Does not treat RAP `freshness: CURRENT` or `conflicts: []` as a claim that every narrative sentence is current sequencing instruction.

## 6. Fork 2 — RAP reduced-cadence / same-merge binding

### Target

Keep RAP **read-only** and **bound to permanent-main truth**. Establish provenance **without a separate sibling human PR** when named authority, execution flags, and other material authority state have not changed. **Material** authority changes still trigger explicit regeneration and verification.

ADR **0026** source-binding remains: an unmerged draft must not represent permanent-main authority. CURRENT still requires the four mandatory sources (`HEDGR_STATUS.md`, `AGENTS.md`, accepted ADR index, `HEDGR_ACTIVE_DOCTRINE_INDEX.md`) present, structurally valid, fresh, and bound to the **same immutable source revision**. Missing or conflicting context still **fails closed**.

### Material RAP change (proposed trigger)

Regenerate and verify RAP when **any** of the following change in the bound sources:

- Named parent `active_ticket_ids`.
- Named nested occupancy in §7 / §7a (even though RAP `active_ticket_ids` currently lists parents only).
- Parallelism pass identity or named concurrent lanes.
- Execution-class / Class A–C / Green-envelope state.
- Financial-capability, live-rail, custody, or customer-money flags.
- Participant publication/distribution flag.
- Doctrine or accepted-ADR membership that RAP’s mandatory sources carry.
- A genuine current-authority conflict (fail closed; do not paper over with a SHA bump).

### Non-material (proposed non-epoch)

A source merge that does **not** change the list above may bind RAP to the new permanent-main SHA through **same-merge or post-merge provenance**, without opening a separate governance epoch:

- **Same-merge:** after source is committed, regenerate RAP bound to that commit SHA in the same change that lands on permanent main, so the merged revision is self-bound; or
- **Post-merge non-epoch bind:** regenerate against the already-merged SHA as a mechanical provenance step that is not treated as a new Founder/HedgrOps authority event.

Unmerged / draft branches still cannot present `CURRENT` for permanent-main history. `pnpm bridge:rap:check` remaining fail-closed when the working mandatory-source set no longer matches the recorded revision is preserved.

### What Fork 2 does not do

- Does not make RAP authoritative.
- Does not relax fail-closed conflict behaviour.
- Does not add general-purpose repo search.
- Does not change generator code, CI, Worker routes, or schema in this design artefact.
- Does not treat `freshness: CURRENT` as occupancy.

## 7. Fork 3 — Bounded Founder-triggered in-ticket reversible amendments

### Target

Once an outcome is **already explicitly named and bounded** in §7 / §7a, Founder-triggered reversible work **inside that existing scope** may proceed as **sequential delivery under that same authority envelope**, provided the unchanged-conditions list holds.

This is **not** standing Green delegation. The Founder still triggers each amendment. §7 still names the occupying ticket. Breach of any unchanged condition returns the work to normal founder/repo authorisation (source record, RAP bind as then in force, distinct verification).

### Unchanged-conditions list (from the Founder Return Brief)

All of the following must remain unchanged for the in-ticket path to apply:

1. Authorised outcome (the occupying named ticket).
2. Execution class.
3. File/surface boundary **or** an explicitly permitted amendment envelope already recorded in the occupying §7a.
4. Trust posture.
5. Data / security posture.
6. Architecture.
7. Material product narrative.
8. Financial capability.
9. Exclusions and stop conditions.

If any item would change, stop. Do not use this path.

### How an in-ticket amendment would work (proposed, not in force)

1. Founder states the amendment (quote recorded in the occupying §7a envelope or a dated amendment note **inside that brief** — not a new nested ticket).
2. Confirm the nine conditions hold. If not, escalate to a normal authority epoch.
3. Deliver sequential reviewed commits under the occupying file/surface boundary.
4. Verify in proportion to consequence: money-path and trust copy keep distinct QA + hermetic tests + hosted checks; decorative presentation inside an already named CSS/copy envelope may use visual/regression against the existing suite without a new RAP epoch.
5. Rollback remains git revert of the scoped commit(s); no state migration.
6. Consuming the amendment does not close the occupying ticket and does not create standing refinement authority.

### What Fork 3 does not do

- Does not revive Green Lane or create inferred standing refinement.
- Does not let agents, Product Assurance, or RAP trigger amendments.
- Does not widen an occupying file list by inference.
- Does not apply automatically to remaining WEEKEND-PREP instrument/rehearsal/release work.
- Does not collapse two nested **runtime** Lane V tickets into one.
- Does not treat shared-baseline-class changes (default + synthetic presentation semantics) as “decorative CSS.” Those are closer to material narrative/surface change and would normally fail condition 3 or 7 unless the occupying brief already named that envelope.

| --- | --- | --- |
| Trust / money / withdrawal / deposit / ledger-adjacent runtime | Distinct Verifier; full hermetic validate; hosted required checks; shipped inspection | Material — regenerate and verify |
| Occupying-ticket instrument / protocol / Form (external) | Existing methods controls; no inferred publication | Material if flags/occupancy change; else occupying process as then in force |

| Docs-only pointer that **does** change named occupancy or flags | Distinct governance review; scoped or full checks as then required | Material |
| This Proposed design file | Advisory only | None — not in force |

This table is design, not CI.
